三、架构评估

官方任务书要求的核心架构原则是："页面只负责提交与观察，执行统一交给 dispatcher"。这一 CQRS 风格的分层在实现中得到了忠实落地。

3.2 架构亮点

纯编排调度器

JobDispatcherStateMachine 自述为 "pure orchestration layer"，零硬编码任务类型分支。四态生命周期（PENDING → RUNNING → COMPLETED/FAILED）跃迁表严格约束，终态不可逆，非法跃迁直接抛异常。

插件化注册表

TaskHandlerRegistry 使用 @register(task_type) 装饰器，Handler 类在模块导入期自动注册。新增任务类型只需实现 BaseTaskHandler 并在 __init__.py 导入，对调度器零侵入。

日志脱敏管道 v2 新增

所有 job.error 经 sanitize_log_text 处理后才写入；job.logs 通过 append_log 接口自动脱敏；环境变量审计经 sanitize_env_dict 仅记录变量名不记录值。满足安全红线第三项。

双定时器自熔断

快轮询（1s）初始关闭，慢轮询（30s）常开保活。任务进入终态后快轮询自动熄灭，但仍执行最后一次全量刷新，杜绝"终态面板缺最后一帧"的竞态。

3.3 架构短板

  • 代码寄居于 smoke/ 目录：全部业务代码位于 smoke/f1/ 下，这是一个 smoke test 命名空间，而非生产包。虽然 Phase 0 报告已承认这一技术债并在 P1 蓝图中规划"架构转正"，但截至目前（HEAD f0ad1be）仍未完成迁移。这会影响外部评审者对工程成熟度的第一印象。
  • core/ 目录非标准包命名空间：JobRequest 等核心模型已提取到 core/schema.py，core/security.py 承载脱敏逻辑，但 core/ 目录仍非标准 ultralytics 包命名空间，导入路径 from core.schema import ... 在包安装后可能不可用。
  • 单进程内存态：JobsManager 使用进程内 dict + threading.Lock 管理任务状态，daemon 线程执行。进程重启即丢失全部任务历史，不支持多 worker 部署。这在 P0/P1 阶段可接受，但生产化需要持久化方案。

七、典型缺陷复盘评估

Phase 0 报告记录了 4 个攻坚事件，以下评估其修复质量和可复现性。

攻坚 1：Gradio DOM 双重挂载

根因：子 Blocks 在激活上下文中实例化后追加 .render()，导致组件二次入 DOM。

修复质量：确立"单挂载原则"，注释即契约。集成测试以布局树断言锁死（组件 ID 全局唯一、文本标记各出现 1 次），从约定升级为可执行不变量。

优秀

攻坚 2：gr.Warning 运行时崩溃

根因：gr.Warning 非 BaseException 子类，raise 必然崩溃，且会终止事件回调。

修复质量：改为 toast 触发 + fallback 返回，全仓库复扫 raise gr.Warning 现存 0 处。

优秀

攻坚 3：时间戳共享与排序失效

根因：Pydantic 类级默认实例导致 created_at 在类加载时冻结，所有任务共享同一时间戳。

修复质量：提交期动态注入 UTC ISO 时间戳。回归测试以 time.sleep(0.1) 级差断言严格逆序且时间戳互不相同。

优秀

攻坚 4：前后端契约解耦

根因：状态 JSON 混入 UI 临时字段，数据契约随语言环境漂移。

修复质量：状态载荷收敛为纯英文标准键，本地化文案物理分层到 banners/toasts。术语"作业"统一校准为"任务"。

优秀

攻坚 5：重置按钮灰色分栏 v2 新增

根因：Gradio gr.Row + gr.Button 并排时，按钮外层 .block 容器自带灰色背景和内边距。

修复质量：统一为 "./ckpts/yolov8n.pt"，三个字段（model_path / data_source / output_dir）初始值与预设完全对齐。

九、优缺点总结

9.1 核心优点

  1. P0 + P1 全部达成：5/5 P0 + 4/4 P1 全部代码实现，无功能缺口。v1 时 P1 为 3/4
  2. 安全红线三项全部满足：Shell 禁用 4 层纵深、路径白名单 + regex 模式 3 层纵深、日志/环境变量脱敏 3 层管道。v1 时脱敏缺失
  3. 架构设计忠实落地：三层解耦（UI → Dispatcher → Handlers）+ 领域模型层（core/），调度器零硬编码任务分支，插件化注册表实现零侵入扩展。
  4. 测试覆盖全面：240 个 pytest 用例覆盖调度器、Handler、Skill、UI、安全脱敏、产物发现全层。UI 不变量（单挂载、双定时器、54 输出绑定）升级为可执行断言。v1 时 171 例
  5. 攻坚修复质量高：6 个典型缺陷均采用"根因定位 → 修复 → 测试锁定不变量"范式。v1 时 4 个
  6. i18n 工程化完善：中英双语 89 键/语言，顶层语言广播驱动 54 个组件重绑定，数据契约与展示文案物理分层。路径校验、重置按钮、刷新按钮全部接入多语言。
  7. 代码规范：ruff 全绿，零 TODO/FIXME 残留，Google docstring 规范。
  8. 文档工程：8 篇 markdown 文档 + Phase 1 交付报告 + job_schema.json，覆盖架构说明、使用指南、缺陷复盘、实现总结。v1 时 6 篇

9.2 核心缺点

  1. 代码寄居于 smoke/ 命名空间：全部业务代码位于 smoke/f1/ 下，而非生产包命名空间。这是最大的结构性技术债，影响工程成熟度评估。
  2. 交付物清单不完整：官方要求的五项交付物中，操作手册和安全测试报告仍未见独立产出。
  3. P1 checklist 与代码不同步：README 中 P1 的 4 项仅勾选 3 项，但 regex 白名单代码已实现。文档滞后影响评审准确性。自 v1 指出至今 3 天未修复。
  4. Git 历史存在重复提交：3 对重复提交消息，已规划 reword 修正但尚未执行。
  5. 无 CI 流水线集成：新增代码未绑定到项目的 CI 配置，测试结果依赖手工执行，存在回归风险。
  6. 单进程内存态：任务状态进程内 dict 管理，daemon 线程执行，无持久化，不支持多 worker 部署。

v1 列出的"敏感环境变量过滤缺失"和"P1 regex 白名单未实现"两项缺点已在 v2 中消除。
